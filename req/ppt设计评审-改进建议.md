## 一、模型层缺口（优先处理）

### 1. OutlineDoc 表达不了复合版式（真实缺口）

§3 的 `OutlineSlide.tips: OutlineTip[]` 是**平铺数组**，没有栏归属/槽位角色。但 §5.4/5.5 的 `columns`（栏结构）、`metric_columns`（上卡+下栏）、`metric_list`（上卡+下清单）都要求结构化分组。现在只能靠 `- col:` / `- metric:` / `- list:` 行前缀在 Markdown 里表达——这恰恰回到了 §2 批评的"元信息塞进 Markdown 行、用户一改就乱"的老问题。

建议：`OutlineTip` 增加槽位路由字段，或按 layout 定义 union 槽位：

```ts
type OutlineTip = {
  text: string;
  sourceRef?: string;
  bucket?: string;
  slotGroup?: string;   // 'col1' | 'col2' | 'metric' | 'list' | ...
};

// 或更彻底：OutlineSlide 按 layout 区分
type OutlineSlide =
  | { layout: 'list'; tips: OutlineTip[] }
  | { layout: 'metric'; metrics: MetricCard[] }
  | { layout: 'metric_columns'; metrics: MetricCard[]; columns: Column[] }
  | ...;
```

编辑 UI 的"要点列表"也要跟着分组渲染，否则用户在 columns 页上移下移一条要点时无法保证不跨栏。

### 2. 防 C 类（漏章漏指标）没有机制

10.2 的改进项都假设"素材已被检索到"，但 C 类根因是**大纲阶段就漏了整章**（属性章、TOP10、爆款趋势全没进大纲）。RAG 漏召回补不回大纲没要求的东西。

建议加**素材覆盖清单（coverage checklist）闸门**：

1. 大纲生成前：从结构化抽取库（P1-4）列出"本主题必选素材清单"——每个数据表/榜单/属性维度至少对应一页；
2. 大纲生成后：校验大纲对清单的命中率，漏项触发补章或显式提示；
3. 验收指标（§7）加一条"素材覆盖率 ≥ X%"。

这与现有的"决策链分章"不冲突：分章管顺序，覆盖清单管不丢。

### 3. 版式枚举缺 table / image_grid，图鉴型素材永远只能变文字卡

layout 枚举（list/metric/columns/metric_columns/metric_list）没有表格和图片网格。源报告是图鉴型（TOP10 榜单、价格带表、商品图墙），这类内容在任何现有版式下都必然退化成文字卡片（C 类"零图零表"）。

建议：
- 枚举预留 `table`（价格带表直填原生表格）和 `image_grid`（榜单/图鉴网格，图片从源 PDF bbox 裁切）；
- 依赖 P0-2 入库时**保存图片资产 + bbox + 页码**——OCR 时这些信息本来就存在，不存就永远丢了；
- image_text 的图来源（ppt生成设计.md 的 4 个来源）应把"知识库附图/bbox 裁切"从第 4 优先提到第 1，图库/生成图做兜底。

### 4. kind: inference 靠标题正则判定太脆

「标题含行动清单/归纳」是事后猜测。既然大纲生成已是三段流水线（结构→选型→填充），`kind` 应该在**结构段就由模型直接输出**为结构化字段，正则只做兜底修正。同理 `layout` 自动推断（"要点含≥2个原数字→metric"）建议也改为"模型生成时输出 + 规则校验修正"，而不是纯规则推断——模型对"这页是不是数据页"的判断比数字计数可靠。

## 二、校验体系：缺"第三道闸"

10.4 已落地的 P0-1 是**大纲层**校验（tips 数字须在本页检索 docs 中出现）。两个漏洞：

1. **子串包含 ≠ 口径正确**："296.2万"确实出现在检索 docs 里，但被写成"销量TOP7合计296.2万"——数字校验通过，事实仍错。校验必须升级为**数值+实体绑定**：数值与其品类/指标实体（衬衫、polo、大盘、TOP、环比/同比）必须来自**同一个 chunk**，跨 chunk 拼装判失败。这正是 A 类错误的形态。
2. **灌模之后没有复核**。大纲校验通过了，填充/渲染阶段（拆 run、跨槽、清空逻辑）仍可能引入错误。建议补"成品闸"：

| 闸 | 时机 | 内容 | 失败动作 |
|---|---|---|---|
| 大纲闸 | 大纲生成后 | schema 校验 + 覆盖清单命中率 + kind/版式合法性 | 补章/重试 |
| 填充闸 | 每页灌数前 | per-slot 忠实性（数值+实体同 chunk）、长度/条数校验、跨槽去重 | 该页重试，不阻塞其他页 |
| **成品闸（缺）** | 灌模完成后 | 用 python-pptx 等抽出生成稿全文：数值复核、槽残留（`{slot}`/`progress`）扫描、空槽清点、文本截断检测 | 页级失败提示 + 回归报告 |

成品闸同时能兜住"字体变白、副标题不上页"这类渲染坑（ppt生成设计.md 提到的已知问题）——至少能**检测**出来并提示，而不是静默出稿。

另外建议把 P0-1 的失败动作明确分级：关键槽（slideTitle）失败→整页重试；可选槽失败→留白+告警；并在每次生成输出 **per-slot 填充报告**（槽名/值/证据 chunk/校验结果），这是后续做 eval 回归的数据基础。

## 三、工程健壮性

### 1. 版面定位（ppt版面定位设计.md）：页码硬编码公式是脆弱点

`页码 = 风格序号 × 3 + (项数 - 3) + 起始页` 隐含"每风格恰好 3 页、项数只认 3–5"；`getTemplatePageNumber` 把布局知识写死在 `PptTemplate.ts`。换模板/插页/补风格时整条公式失效，且编译期发现不了。

建议：**模板 manifest 化**——模板入库/更新时扫描一遍（制作时按约定给每页命名，如 `slide name = metric_3card` 或放隐藏标记文本），生成 `template-manifest.json`：

```json
{ "page": 26, "layout": "metric", "cards": 3, "slots": ["slideTitle","vItem.item1","vItem.item1_Desc","..."] }
```

运行时查 manifest 而不是算公式。好处：① 换模板零代码改动；② manifest 里的 slots 清单直接就是填充闸的校验依据；③ 三份文档里的页码对照表不再需要手工维护（见第四节）。

### 2. 占位符拆 run：在模板制作规范里根治

"占位符拆 run 折磨"（ppt生成设计.md）应在源头解决：模板制作规范强制"占位符必须单 run、所在文本框无富文本混排"，模板入库时自动扫描 `slideN.xml` 校验占位符完整性（发现被拆 run 自动合并修复）。一次工程化，胜过运行时各种兜底。

### 3. metric_columns 组合覆盖不全

模板只有 2–5 卡+2 栏（32–35）和 5 卡+3 栏（36）两种组合。内容常出现 3 卡+3 栏、4 卡+3 栏等，需要明确**降级规则**（降到 2 栏？拆 metric_list？），写进选型约定，否则选型 Agent 会选出模板里不存在的组合。

### 4. 领域包注入缺冲突仲裁

分层写入约定（勿串层）很清晰，但没定义**层级冲突时谁赢**：领域禁忌 vs 骨架规则、变量层要求 vs 领域决策链。建议明确优先级（一般：骨架硬约束 > 领域 > 变量；或在领域包定义里显式声明可覆盖项），否则多包组合后 prompt 行为不可预期。同时给领域全文设 token 预算，超限时的裁剪顺序也要定（先裁领域示例、后裁规则）。

## 四、文档一致性

1. **页码对照已过期**：ppt版面定位设计.md 说第 37–41 页"未使用（restSlide）"，但 000 设计 §5.5C 说 metric_list 用 37–41"已落地"。两文档必有一份过期——印证了第四节建议：页码对照表应由 manifest 自动生成，文档只引用不手写。
2. **layout 枚举三处陈述需同步**：000 §3 枚举、§5.4/5.5 版式约定、版面定位的模板页表，新增版式时要三处同步，容易漏。建议以代码/manifest 为唯一真源。
3. **验收标准（§7）未指标化**：建议直接映射为衬衫/polo 样例的 eval 用例（该样例已有页码级金标），每次管线变更跑回归：数值准确率、素材覆盖率、坏填充率、幻觉率四个数。§10.2 P2 提了但没定义执行方式。

## 五、小项

- `pageTarget: string`（"12～15"）——建议存 `{min, max}`，大纲生成后硬校验章/页数，避免模型自由发挥。
- 开放问题 2（localStorage JSON 体积）：OutlineDoc 体积很小（几十 KB 级），建议直接迁服务端存储，不要在 localStorage 上再做兼容逻辑，省一条迁移路径。
- 开放问题 3（出处页码映射）：**不算高成本**——VL OCR 解析时页码已知，入库写进 chunk 元数据即可得到"文件名+页码"，建议直接做，不必当开放问题。
- 10.4 的落地顺序建议正确：先上"拦错"（成品闸 + 占位清理），再动入库模型（P0-2/P1-4，需重建向量）。唯一补充：**图片资产 + bbox 保存应随 P0-2 一起做**，否则 VL 重跑一次后还要再重跑一次才能补图。
