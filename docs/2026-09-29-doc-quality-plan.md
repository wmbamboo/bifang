## 任务 4（P1）· 检索跨页去重 B4 —— ⚠️ 语义已修正

> **2026-09-29 复核修正**：本节原写法（"跨页调用方透传 `used_chunk_ids`，全文生成器按页循环时累计"）**前提不成立**——前端没有"逐页循环"，见「任务 4B·4B.3 的 ⚠️」。
> 保留本节，但把它降为 **4B 的一个子步骤（页内去重 + 只读入参）**；跨页协调状态**不得**落在本函数或 `kb_service` 模块作用域内。

**涉及文件**
- `services/kb_service.py:1324`（`retrieve_for_writing`）、`kb_service.py:176`（向量库 `search`）

**实测事实（复核确认，供 Cursor 核对）**

| 事实 | 证据 |
|---|---|
| 每次 HTTP 请求 = 一次独立检索 | `routers/chat.py:103-112` 收到请求即调 `retrieve_for_writing` |
| 一次调用只服务一页 | `kb_service.py:1206-1246` 解析「【本页标题】/【大纲要点】」后仅返回该页片段 |
| 去重只在函数内、返回即销毁 | `kb_service.py:1461-1469`，`merged` / `seen` 均为局部变量 |
| 单段注入上限 14 片 | `kb_service.py:1596` `merged[: settings.writing_context_limit]`；`config.py:50 = 14` |
| 跨调用零状态 | 全仓 grep `used_chunk\|seen_chunk\|chunk_ledger` → **0 命中** |
| 现签名**无**账本参数 | `kb_service.py:1324-1332`：`user_text, knowledge_base_name, top_k, score_threshold, mode, source_files, retrieval_scope` |

**实现要点（修正后）**
1. 跨页去重**必须由调用方持有状态**：`retrieve_for_writing` 只增加**只读入参** `exclude_keys: set[str] | None = None`。**禁止**新增模块级变量、全局 set 或进程内缓存——会把不同会话互相污染。
2. 页内去重：召回 top_k 后，相邻 chunk embedding cosine > 0.92 只保留来源页码更靠前的一条（此条与跨页无关，可独立先合）。
3. 跨页配额：同一 `chunk_id` 全文最多命中 1 次 → **降权而非删除**（键为 `_doc_key`，`kb_service.py:1271`；直接删除会让"唯一证据页"饿死）；同一数字指纹全文最多出现 2 次（正文+表格）。
4. 去重日志写 `gate_report.dedup`，便于评估召回质量。

**验收（新增 `backend/tests/test_retrieval_dedup.py`）**
1. 单次调用内：构造 4 个高相似价格带 chunk → 返回两两 cosine ≤ 0.92。
2. 传入 `exclude_keys` → 返回集合与入参**无交集**。
3. **不传** `exclude_keys` → 输出与现状逐字节一致（防回归）。

## 任务 4B（P1）· 材料池 + 分段分配器（架构）B4 根因

> 承接任务 4。**诊断结论：分段生成不是病因，分段检索才是**——真正的缺口不是「别分段」，而是分段之后**没有任何跨段协调状态**。
> 任务 4 解决"同一片段别重复用"；本节解决"**材料如何被全局分配**"。建议 4B 先合（它定了"分配表从哪来"），任务 4 的 `exclude_keys` 才有真正的调用方。

### 4B.0 归因边界（别把无关 bug 记到检索头上）

| 现象 | 归因 | 说明 |
|---|---|---|
| 12 张表约 4 张同表换列序 | ✅ 直接 | 跨页独立召回同一 chunk（B4） |
| 章节反复复述同一组数字 | ✅ 直接 | 同上 + 无账本 |
| 材料覆盖不均（有的点查 10 片、有的 0 片） | ✅ 直接 | 无全局分配，靠单页相似度碰运气 |
| 实体张冠李戴（B2 `7,280.1万`） | ⚠️ 部分 | 单段视野窄，看不到邻页"这数属大盘"的对照；但根子仍是缺实体闸（任务 2） |
| 标题丢字 polo/200（B1） | ❌ | 前端 `ViewItem4Doc.ts:15-24` 字符清洗链，与检索无关（任务 1） |
| 落肩袖误当第一（B3） | ❌ | 图表内排名推理，单段内同样会错（任务 3） |
| 引用格式混用（B5） | ❌ | 格式化产出口 `kb_service.py:907/929`（任务 5） |
| 空表格 / OCR 噪声（B6） | ❌ | 占位符填充与清洗（任务 6） |

### 4B.1 最有力旁证：那 60 行 prompt 规则在替架构补洞

`kb_service.py:1627-1692` 的 `_TASK_SUMMARY` 里，**8 条以上规则在描述同一件事**——"片段边界被切坏 + 单段视野太窄"：

| 规则行 | 原文（摘） | 它在替谁补洞 |
|---|---|---|
| `:1641` | 「片段开头或结尾常常粘着上一节或下一节…不要并进当前章节」 | 片段边界 |
| `:1643` | 「出现『情境/打法/案例』时…不要改挂到旁边的小节标题上」 | 片段边界 |
| `:1659` | 「小点描述不要重复【当前章节】和【本页标题】里已经写过的话」 | 单段视野 |
| `:1660` | 「各小点描述必须互不雷同：禁止把同一段案例粘到多个小点后面」 | 无分配器 |
| `:1671` | 「禁止只摘中间两项漏掉第一名」 | 无分配器 |
| `:1677` | 「同一片段常并排大盘与子类数字：页标题写大盘则只用大盘数」 | 单段视野 / 缺实体闸 |

这些不是文风要求，是**用自然语言人肉实现了一个本该由「分配器」承担的职责**。且它们只能约束段内可见的东西——`:1659` 只能对比"当前章节和本页标题"，**看不到别的页已经写过什么**。规则越写越长，恰恰说明架构缺口一直没补。

### 4B.2 "上下文限制"这个前提今天已经过期

- 当年（4k–8k 窗口）分段是对的，但**检索的规模从来不等于上下文的规模**：一次拿 200 个候选片段也就几十 KB。受上下文约束的是**生成**，不是**检索**。
- 这条约束被多传导了一层，变成"检索也要分段"——而检索分段**既不必要，当年也没给它配任何跨段协调机制**。
- 结论：**保留分段生成**（流式体验与输出稳定性都需要），**把检索改回一次做完**。

### 4B.3 正确形态（四相）

1. **全局建池**：一次检索（主题 + 章节骨架），取宽候选 200–300 片。
2. **按章节分配**：章节标题/要点 与池内片段匹配打分，产出「章节 → 片段」表；**纯启发式即可，不必加 LLM 调用**。
3. **分段生成**：每段只从分配给它的片段里取（段落路径改为消费"已分配片段"，而非重新检索）。
4. **全局账本**：`used_chunk_ids` 跨段累计，已用**降权**；**从未被选中的片段进覆盖闸报告**（覆盖闸是前端既有三道闸之一）。

> ⚠️ **实现落点必须避开一个坑**：当前前端是 `Promise.allSettled` **全并行**发段——`AiOutlineGenDoc.tsx:250-287`（循环所有段落 `promiseArr.push(axios.post(...))` 后一次性 `allSettled`）、`KbOutlineGenDoc.tsx:321` 同形。**不存在"生成第 N 页之前"这个时刻**。所以：
> - ❌ **不要**在段循环里"读同会话历史账本"——并行时没有任何一段能看到别的段的结果；且本批消息要到批结束才落库（`chat_service.bat_add_msgs`），生成期间历史里根本没有本批。
> - ❌ **不要**把账本放进 `kb_service` 模块作用域 / 进程缓存——会跨会话污染。
> - ✅ 账本与分配表由**阶段 2 一次算完**，随每段请求一起下发；或把 **1+2 合成一个新端点**（一次请求返回全篇「章节→片段」分配），前端再逐段带着分配结果调用。两条路都可，二选一，别混。

### 4B.4 账本存储：通道是"插座"，不是"现成数据"

- `chat_service.py:94-99` 的 `bat_add_msgs(payload)` 会读 `payload["last_acc_docs"]`，并在 `:128-132` / `:157-160` 写入 `chat_msgs.extra["ret_docs"]`；`extra` 是 JSON 列，加字段**不需要 schema 迁移**。
- **但复核实测**：全仓（忽略大小写）grep `last_acc_docs|ret_docs` **仅命中 `chat_service.py` 自身** → **前端 0 处发送（无生产者）**、**后端 0 处读取（无消费者）**。且写回是"整会话 `DELETE` 后全量重插 + 把**同一个** `last_acc_docs` 盖到**每一条** assistant 消息上"，**粒度是单块、不是按页**。
- 准确表述：**写回钩子与 JSON 槽位现成，数据没有、粒度也不对**。接账本时需同时补：① 生产者（前端在阶段 2 后提交分配/使用表）；② 按页粒度（用 `extra["ret_docs_by_page"]` 这类新键），**不要复用** `last_acc_docs` 的"盖全量"写法。
- 若不走数据库：账本也可只在**前端一次生成流程内**驻留内存（阶段 2 产出 → 阶段 3 消费 → 阶段 4 出覆盖报告），**不需要持久化**。通常这才是最小改动。

### 4B.6 陷阱：别把分配器建在现有词表硬编码之上
`kb_service.py:1215-1246` 的页级路由**已经是领域硬编码**：`if title and "大盘" in title and "男装大盘" not in extras: extras.append("男装大盘")`，以及 `男士衬衫` / `polo衫` / `价格带` / `面料|材质|属性|图案|厚薄|袖型` 的显式分支。
→ 分配器若直接复用它做"章节→片段"打分，会把这套**服装领域词表固化成架构的一部分**（正是 B1 同族的"改品类就要改代码"问题）。**4B 的分配打分应基于通用信号**（章节标题与片段的词面/向量相似度 + 章节在骨架中的位置 + 片段页码邻近性），领域词只作为**可选 profile 注入**（呼应任务 2 的"词面规则应隔离为 per-domain profile"）。

### 4B.7 验收（新增 `backend/tests/test_material_pool.py`）
